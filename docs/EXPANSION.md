# 확장 계획

작성일 2026-11-13 · 개발 보고서([REPORT.md](REPORT.md), R1 완료·R2 진행 중) 기준. 사용자가 전달한 계획을 그대로 옮겨 적은 문서다.

기능을 더 붙이기 전에 부서별 화면 구조부터 정리하고, 보안 게이트(R3)를 통과해 오픈한 뒤에 메시지 발송 → 외부 예약 유입 순서로 확장한다. EMR은 CRM과 규제 수준이 달라서 같은 계획에 넣지 않고 따로 판단한다.

## 권장 순서

| 순서 | 내용 | 실제 환자 데이터 | 비고 |
| --- | --- | --- | --- |
| 1 | 화면·권한 구조 정리 (S-1~S-7) | 필요 없음 | 지금 바로. 이 기간에는 새 기능 추가를 멈춤 |
| 2 | R2 남은 Task → R3 보안 게이트 → R4 이관·오픈 | R4부터 | 기존 계획 그대로 |
| 3 | 메시지 자동 발송 (M-1~M-5) | 필요 | 채널 개설·템플릿 심사는 2번과 병행해 미리 준비 |
| 4 | 온라인 예약 페이지와 예약 접수함 (B-1~B-5) | 필요 | 카카오 채널·네이버·보이는 ARS가 모두 이 페이지로 연결 |
| 5 | 네이버 예약·카카오톡 예약하기 직접 연동 | 필요 | 제휴 가능 여부를 각 사에 문의한 뒤 결정 |
| 별도 | EMR | 필요 | 법률·인증 검토 후 별도 프로젝트로 판단 |

3~5번은 모두 실제 환자의 전화번호를 다루거나 외부에서 서버로 들어오는 입구를 여는 일이다. 그래서 R3 통과 전에는 개발과 시험(직원 본인 번호)까지만 하고, 운영 투입은 R3 이후로 한다.

## 1. 부서별 화면: 권한에 따라 보이는 것만 다르게

화면은 한 벌만 만들고, 각 메뉴·영역·버튼에 '필요한 권한'을 붙여서 로그인한 사람의 권한에 맞는 것만 보이게 한다. 부서마다 화면을 따로 만들지 않는다.

### 구조

- **권한:** '예약 고치기', '상담 보기', '통계 보기'처럼 작은 단위의 능력. 코드 한 곳(권한 목록 파일)에만 정의한다.
- **부서:** 권한 묶음 + 로그인 후 첫 화면 + 메뉴 구성. 부서는 프론트·상담·진료·운영 4개.
- **개인 추가 권한:** 부서 기본값에 더해 사람별로 권한을 더할 수 있다. 예: 원장 = 진료 부서 + '통계·실적 보기'.
- **화면 등록부:** 모든 메뉴와 화면 영역을 한 파일에 등록하고 각각 필요한 권한을 적는다. 화면은 이 등록부를 권한으로 걸러서 그린다.
- **서버가 최종 차단:** 화면에서 숨기는 것은 편의일 뿐이고, 지금처럼 서버의 권한 검사(defineRoute)가 실제 차단을 맡는다. 서버와 화면이 같은 권한 목록을 쓰므로 둘이 어긋나지 않는다.
- **금지:** 화면 코드에서 `부서 == 프론트` 같은 직접 비교를 쓰지 않는다. 테스트로 막는다.

### 부서별 메뉴 (초안)

| 부서 | 첫 화면 | 보이는 메뉴 | 하는 일 |
| --- | --- | --- | --- |
| 프론트 | 내원 보드 | 내원 보드, 예약 캘린더, 고객 | 예약 등록·변경, 내원 상태, 고객 등록 |
| 상담 | 상담 보드 | 상담 보드, 예약 캘린더, 고객 | 상담 기록, 수술예약 전환, 예약 등록 |
| 진료 (의사·간호) | 오늘 진료 일정 | 오늘 일정, 수술 기록 | 일정 보기, 내원 상태(간호), 수술 참여 직원, 수술 메모(의사) |
| 운영 | 통계 | 통계·실적, 편집, 직원, 가져오기, 감사 로그 + 위 메뉴 전체 | 설정, 계정, 데이터, 점검 |

지금의 역할 5개(프론트·상담·원장·간호·관리자)는 다음처럼 옮긴다: 원장·간호 → 진료, 관리자 → 운영. 원장이 통계와 상담을 보는 것은 개인 추가 권한으로 유지한다. 부서별로 무엇을 보여줄지는 병원에서 확정해야 하는 값이라, 위 표는 보고서의 현재 권한표를 옮긴 초안이다.

### 화면이 복잡해진 부분의 정리 원칙

- 추가 권한이 없는 프론트·상담·진료 직무의 상단 메뉴는 4개 이하. 여러 부서의 화면을 보는 관리자·원장은 넘어도 된다. 권한이 있는 메뉴를 개수 때문에 숨기지 않는다(2026-11-13 수정). 설정과 가끔 쓰는 관리 기능(가져오기 등)은 [편집] 한 곳에만 둔다.
- 캘린더의 표시 옵션(칸 크기, 과별 묶음, 색 기준)은 '보기 설정' 버튼 하나로 모은다.
- 예약 상세는 권한 단위 영역으로 나눈다: 기본 정보 / 상담·할인 / 수술 참여 직원 / 수술 메모. 권한이 없는 영역은 아예 그리지 않는다.
- 색 규칙(라벨 > 항목 > 상태)처럼 피드백으로 겹겹이 쌓인 규칙은 화면에 범례로 한 번만 보여준다.

- 직무별 권한은 코드가 아니라 DB에 두고 관리자가 편집한다(S-2b 추가).
- S-7은 직무 × 권한 편집 화면으로 넓힌다.
- 예약 금액 보기는 기본값을 상담·운영·원장으로 두는 권한으로 S-3에 넣는다.
- 설정으로 풀 수 없는 고정 규칙은 [CHECKLIST.md](CHECKLIST.md) S 절에 적었다: 권한 관리자 0명 방지, 권한 변경 감사 로그, 로그 수정·삭제 권한 없음, 민감 권한 확인, 새 권한 기본 꺼짐.

**진행 규칙:** S-2·S-3·S-6처럼 동작을 바꾸지 않는 정리와, S-4·S-5처럼 화면이 달라지는 변경을 한 커밋에 섞지 않는다. S Task가 끝날 때까지 새 피드백은 docs/FEEDBACK.md에 적어만 둔다.

## 2. 메시지 자동 발송 (카카오 알림톡·문자)

예약 안내와 리마인더는 카카오 알림톡으로 보내고, 실패하면 문자로 대신 보낸다. 알림톡은 카카오와 직접 계약하지 않고 공식 딜러사(발송 대행사)의 API를 통해 보낸다.

### 미리 준비할 것 (개발과 별개로 병원이 진행)

- 카카오톡 비즈니스 채널 개설과 비즈니스 인증
- 발송 대행사 선정·계약, 발신프로필 등록
- 알림톡 템플릿 작성과 카카오 심사. 알림톡은 사전 승인된 템플릿으로만 보낼 수 있다
- 문자 발신번호(병원 대표번호) 등록

### 보낼 메시지

| 메시지 | 시점 | 성격 | 채널 |
| --- | --- | --- | --- |
| 예약 확정 안내 | 예약 등록 직후 | 정보성 | 알림톡 → 실패 시 문자 |
| 예약 리마인더 | 전날, 당일 오전 (병원 설정) | 정보성 | 알림톡 → 실패 시 문자 |
| 예약 변경·취소 안내 | 변경 직후 | 정보성 | 알림톡 → 실패 시 문자 |
| 다음 예약일 안내 | 진료 완료 후, 다음 예약이 이미 잡혀 있을 때 | 정보성 | 알림톡 → 실패 시 문자 |
| 정기검진·스케일링 리콜 | 마지막 내원 후 일정 기간 | 광고성으로 볼 수 있음 | 수신 동의자에게만 |
| 이벤트·할인 안내 | 수시 | 광고성 | 수신 동의자에게만 |

알림톡은 정보성 메시지만 보낼 수 있고, 광고성 내용이 중심이면 템플릿 심사에서 반려된다. 카카오는 2026년 11월 1일 알림톡 심사 가이드를 바꿨으므로, 리콜 문구가 정보성으로 인정되는지는 발송 대행사와 심사 과정에서 확인한다. 광고성 메시지에는 수신 동의, 야간 발송 제한, 수신 거부 방법 안내가 따른다.

### 구조

- **발송 대기열:** 예약이 생기거나 바뀌면 '보낼 메시지'를 DB 대기열에 넣고, 별도 작업자가 꺼내 발송한다. 발송 업체 장애가 예약 화면을 멈추지 않는다.
- **중복·오발송 방지:** 같은 예약·같은 종류는 한 번만 발송. 예약이 변경·취소되면 대기 중인 리마인더를 자동 취소.
- **시간 제한:** 병원이 정한 발송 가능 시간대에만 발송.
- **기록:** 누구에게 무엇을 언제 보냈고 성공했는지 남긴다. 고객 상세에서 확인 가능.
- **시험 모드:** 허용 목록에 있는 번호(직원 본인)로만 실제 발송. R3 통과 전에는 이 모드만 사용.
- **내용 최소화:** 메시지에는 병원명·날짜·시간만 넣고 진료 항목·금액은 넣지 않는다. 다른 사람이 휴대폰을 볼 수 있기 때문이다.

| ID | Task | 완료 기준 |
| --- | --- | --- |
| M-1 | 발송 대기열 테이블과 작업자, 발송 기록 | 발송 업체를 가짜로 바꿔 끼운 테스트에서 재시도·중복 방지 통과 |
| M-2 | 발송 대행사 API 연결(알림톡, 문자 대체 발송). API 키는 환경변수·Secrets Manager | 시험 모드에서 직원 번호로 실제 수신 확인 |
| M-3 | 예약 확정·리마인더·변경·취소 자동 발송 규칙, 예약 변경 시 대기 메시지 취소 | 예약을 옮기면 이전 리마인더가 취소되고 새 리마인더가 잡힘 |
| M-4 | [편집]에 메시지 설정: 발송 시점, 가능 시간대, 템플릿 연결, 켜고 끄기 | 운영 부서만 접근, 변경이 감사 로그에 남음 |
| M-5 | 광고성 메시지: 수신 동의자만 대상, 야간 차단, 수신 거부 처리 | 미동의 고객이 대상에 포함되면 실패하는 테스트 |

## 3. 외부 예약 유입 (카카오·네이버·전화)

자체 온라인 예약 페이지를 하나 만들고, 카카오 채널·네이버·보이는 ARS가 모두 그 페이지로 연결되게 하는 것이 가장 확실하다. 네이버 예약과 카카오톡 예약하기에 직접 연동하는 것은 제휴가 필요해 보여서 각 사에 먼저 문의해야 한다.

### 채널별 가능 여부

| 채널 | 연동 방식 | 자체 개발 CRM에서 | 다음 행동 |
| --- | --- | --- | --- |
| 자체 온라인 예약 페이지 | 우리가 만드는 웹 페이지 | 가능 | B-1~B-3으로 개발 |
| 카카오톡 채널 메뉴·챗봇 | 채널 메뉴에 예약 페이지 링크, 또는 챗봇이 우리 서버를 호출 | 가능 | 채널 개설 후 링크 연결 |
| 보이는 ARS | 병원 번호로 전화하면 문자로 링크가 가고 화면에서 예약 메뉴를 고르는 방식. 통신·콜센터 솔루션 업체가 제공 | 링크를 예약 페이지로 연결하면 가능 | 솔루션 업체 선정, 링크 연결 지원 확인 |
| 음성 ARS(버튼 입력) 예약 | 솔루션 업체의 연동 기능에 따름 | 업체별로 다름 | 업체에 외부 시스템 연동 지원 문의 |
| 네이버 예약 | 차트·CRM 업체가 네이버 예약 공식 제휴사로 등록해 연동하는 사례가 일반적 | 직접 연동 가능 여부 불확실 | 네이버에 문의. 안 되면 네이버 플레이스에 예약 페이지 링크 |
| 카카오톡 예약하기 (병원) | 공식 협력사(굿닥)를 통한 방식 | 직접 연동 어려울 가능성 | 협력사 경유 조건 확인 |

덴트웹에는 네이버 예약 연동 설정 메뉴가 이미 있다. 네이버 예약을 덴트웹과 CRM 양쪽에 받으면 이중 예약이 생기므로, 예약은 CRM 한 곳에서만 받는 것으로 정한다.

### 예약 접수함

외부에서 들어온 예약은 캘린더에 바로 넣지 않고 예약 접수함에 쌓는다. 프론트가 확인하고 체어와 담당을 정해 확정한다.

- 체어·의사 배정과 진료 소요시간은 사람이 판단해야 하는 경우가 많다.
- 같은 사람인지(기존 환자 매칭) 확인하고 넣어야 고객이 중복 등록되지 않는다.
- 잘못 입력했거나 장난으로 넣은 예약이 캘린더를 막지 않는다.
- 운영이 안정되면 스케일링·검진 같은 단순 항목만 자동 확정으로 바꿀 수 있다.

### 공개 입구의 보안

지금 서버는 병원 IP에서만 접속된다. 예약 페이지는 누구나 열 수 있어야 하므로, CRM 본체는 그대로 닫아 두고 공개용 예약 서비스를 따로 둔다.

- 공개 예약 서비스는 별도 주소·별도 프로그램으로 띄우고, '접수 넣기'와 '빈 시간 보기'만 할 수 있다. 환자 조회 기능 자체가 없다.
- DB 계정도 분리해 접수함 테이블에만 쓸 수 있게 한다. 공개 서비스가 뚫려도 환자 정보를 읽을 수 없다.
- 빈 시간은 '가능/불가'만 보여주고 다른 환자 정보는 내보내지 않는다.
- 예약 전에 휴대폰 문자 인증으로 본인 확인. 요청 횟수 제한과 자동 입력 방지를 건다.
- 화면에서 개인정보 수집·이용 동의를 받고 동의 이력에 남긴다.
- 외부 업체가 우리 서버를 호출하는 경우(챗봇·ARS)는 서명 검증과 발신 IP 제한을 건다.
- 이 시점에 웹 방화벽(WAF)을 도입한다('비용 계획'의 '나중에 올릴 구성').

| ID | Task | 완료 기준 |
| --- | --- | --- |
| B-1 | 예약 접수함: 테이블, 프론트 화면(확인·확정·거절), 기존 환자 매칭 제안 | 확정하면 캘린더에 예약이 생기고 유입 채널이 기록됨 |
| B-2 | 공개 예약 서비스 분리: 별도 프로그램, 접수함 전용 DB 계정, 빈 시간 조회 API | 공개 서비스의 DB 계정으로 환자 테이블 조회가 실패하는 테스트 |
| B-3 | 온라인 예약 페이지: 항목·날짜·시간 선택, 문자 본인 확인, 동의 화면, 횟수 제한 | 휴대폰 화면에서 예약 완료, 같은 번호의 반복 요청 차단 |
| B-4 | 채널 표시: 링크에 채널 구분값(카카오·네이버·ARS)을 붙여 유입 경로 통계에 반영 | 통계에서 채널별 접수·확정·내원 수 확인 |
| B-5 | 외부 호출 수신(챗봇·ARS 업체): 서명 검증, 발신 IP 제한, 접수함으로 전달 | 서명이 틀린 요청은 거부되고 감사 로그에 남음 |

## 4. EMR(전자차트)을 같은 서버에 넣는 문제

지금 계획에는 넣지 않기를 권한다. EMR은 CRM에 기능을 더하는 수준이 아니라 법적 요건·인증·운영 구조가 달라지는 별도 프로젝트다. 덴트웹을 대체하려면 진료기록뿐 아니라 보험 청구와 영상 장비 연동까지 다시 만들어야 한다.

| 쟁점 | 내용 | 지금 CRM과의 차이 |
| --- | --- | --- |
| 진료기록의 법적 요건 | 전자의무기록은 전자서명이 기재된 전자문서여야 하고, 추가 기재·수정 시 접속기록을 별도로 보관해야 한다 | 지금 CRM은 진료기록을 저장하지 않도록 설계했다(절대 규칙 3) |
| 보험 청구 | 진료비 청구 소프트웨어는 심평원의 검사·인증 대상이다. 자체 개발 소프트웨어도 검사를 받는 절차가 있다 | 청구 기준이 수시로 바뀌어 계속 따라가야 한다 |
| 클라우드 보관 | 진료기록의 외부 보관에는 무중단 백업·네트워크 이중화 같은 시설·장비 기준이 있다 | 서버 1대로 시작하는 지금의 저비용 구성으로는 맞추기 어렵다 |
| 클라우드 인증 | 클라우드 EMR의 제품 인증은 클라우드 보안인증(CSAP)을 요건으로 한다. 2020년 보도 기준 AWS 등 해외 클라우드는 미취득 | AWS 서울 리전 사용 가능 여부를 현재 기준으로 다시 확인해야 한다 |
| EMR 인증제 | 인증 자체는 의무가 아니며 사용인증을 받은 의료기관은 약 11% | 인증을 받지 않더라도 의료법의 기록 요건은 지켜야 한다 |
| 덴트웹 '분석' | 사용자로서 화면과 업무 흐름을 정리하는 것은 요구사항 조사다. 프로그램을 뜯어보거나 DB 구조를 추출하는 것은 이용약관·저작권 문제가 될 수 있다 | 계약서 확인 필요 |

위 내용은 기획 참고용이며 법률 자문이 아니다. 일부 출처는 오래된 기사라서, 추진하려면 현행 법령과 고시를 기준으로 법률 검토부터 받아야 한다.

### 대신 지금 해둘 것

- CRM 구조를 정리할 때(S-2, S-3) 기능을 모듈 단위로 나눠 두면, 나중에 진료 모듈을 별도로 붙이기 쉽다.
- 환자 식별은 계속 덴트웹 차트번호로 맞춘다. 나중에 어떤 차트를 쓰든 연결 기준이 된다.
- EMR 추진을 결정하면 그때 서버 구성(이중화, 클라우드 선택)과 비용 계획을 새로 잡는다.

## 5. 보안: 무엇이 달라지나

| 변화 | 지금 | 확장 후 | 대응 |
| --- | --- | --- | --- |
| 외부에서 들어오는 입구 | 병원 IP에서만 접속 | 예약 페이지와 업체 호출을 인터넷에서 받음 | 공개 서비스 분리, 접수함 전용 권한, WAF, 서명 검증 (3장) |
| 외부로 나가는 환자 정보 | 없음 | 발송 대행사·ARS 업체에 이름·전화번호 전달 | 위탁 계약, 처리방침에 위탁 공개, 전달 항목 최소화, 업체별 API 키 분리 |
| 다루는 정보의 수준 | 예약·내원·상담 | EMR을 넣으면 진단·처방까지 | EMR은 별도 프로젝트로 분리 (4장) |

변하지 않는 원칙:

1. R3 보안 게이트가 먼저다. 메시지와 예약 유입은 실제 환자 번호를 다루므로 R3 통과 전에는 운영하지 않는다.
2. 외부 업체의 키와 비밀값은 저장소에 두지 않는다(절대 규칙 2).
3. 외부에서 들어온 데이터는 접수함을 거쳐 사람이 확인한 뒤 본 데이터가 된다.
4. 새 기능도 전부 권한 검사와 감사 로그를 거친다(절대 규칙 4).
