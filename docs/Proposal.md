1. 개요
병원 전용 CRM을 자체 개발하되, 시중 제품이 공통으로 갖춘 기능은 그대로 가져오고 '예약 → 실제 내원 여부'를 프론트 직원이 즉시 입력하는 체크인 기능을 핵심 차별 기능으로 둔다.
• 왜 내원 여부가 핵심인가: 예약 건수만으로는 실제 매출·마케팅 성과를 알 수 없다. 노쇼율, 채널별 실내원율, 상담 실장별 전환율은 모두 '실제로 왔는가'라는 한 칸의 데이터에서 출발한다.
• 사용자: 프론트(데스크)·코디네이터, 상담실장, 원장/경영진, 마케팅 담당자.
• 범위: 고객(환자) 정보, 예약, 내원 체크인, 상담, 수납, 리콜/메시지, 통계. 진료기록(EMR)은 기존 전자차트와 연동하는 것을 기본으로 한다.
확정된 조건: 치과, 1개 지점, 전자차트는 덴트웹 사용, 기존 CRM은 계약 종료 후 데이터 이관 예정. 치과 특성상 정기검진·스케일링 리콜(예: 6개월 주기)과 치료 단계별 다음 예약 관리가 리콜 기능의 중심이 된다.
2. 시중 CRM 분석
국내 병원 CRM은 '전자차트+고객관리 통합형'이 주류이고, 해외는 범용 CRM에 의료 기능을 얹은 형태가 많다. 어느 쪽이든 공통 축은 예약 관리 → 노쇼 방지(리마인더) → 사후관리(리콜) → 성과 통계다.

시중 제품에서 확인된 공통 사용 방식
• 예약은 여러 채널에서 들어와 한 곳에 모인다. 전화·홈페이지·플랫폼 앱 예약이 CRM으로 자동 유입되고, 연락처 기준으로 기존 환자 차트에 붙거나 신규 차트가 생성된다.
• 노쇼 방지는 리마인더 중심이다. 한 업계 분석에 따르면 자동 메시지만 보낼 때 노쇼율은 약 24%, 리마인더가 없으면 39%, 직접 전화 확인 시 약 3% 수준이다(미국 기준).
• 노쇼율은 의사·시간대·지점별로 분석한다. 예를 들어 특정 요일·시간 슬롯의 노쇼율이 높으면 예약 정책을 바꾸는 식이다(eSEOspace).
• 사후관리를 자동 '숙제'로 만든다. 시술 후 주의사항, 재방문 리콜, 생일 메시지 같은 후속 업무가 누락되지 않게 한다.
• 정보성/광고성 메시지를 분리한다. 예약 안내는 알림톡, 이벤트성 메시지는 수신동의자에게만 보내는 구조가 일반적이다(크몽 사례).
시중 제품의 공백 — 우리가 메울 부분
대부분의 제품은 예약 '접수'와 '리마인더'에 강하지만, 내원 확인은 접수 화면의 부수 기능으로 처리되는 경우가 많다. 그 결과 노쇼·지각·당일 취소·무단 변경이 한 상태로 뭉쳐 통계가 부정확해진다. 우리 CRM은 내원 상태를 별도 단계로 정의하고, 프론트가 한 번의 클릭으로 기록하게 만든다.
3. 병원 CRM 업무 흐름
고객 여정은 문의 → 상담 → 예약 → 리마인더 → 내원 확인 → 진료 → 수납 → 리콜로 돌고, 그 가운데 '내원 확인'이 유일하게 사람이 직접 판정해야 하는 분기점이다.
내원으로 기록되면 원내 진행·수납·리콜로 이어지고, 미내원(노쇼·당일취소)이면 사유와 함께 재예약 연락 대상으로 넘어간다. 예약 변경은 원 예약과 연결된 새 예약으로 다시 들어온다.
4. 핵심 기능: 내원 확인(체크인)
프론트 직원은 '오늘 예약 목록'에서 고객 행 하나에 버튼 한 번으로 내원 상태를 기록하고, 시스템은 시각·입력자를 자동 저장한다. 예약 시각이 지나도 미입력이면 자동으로 '미확인' 경고를 띄워 누락을 막는다.

4-2. 프론트 화면 구성 (오늘의 내원 보드)
• 상단 요약: 오늘 예약 N건 · 내원 N · 대기 N · 노쇼 N · 미확인 N (실시간 갱신).
• 목록: 예약 시각순. 열 = 시간, 고객명(마스킹), 신규/재진 배지, 예약 항목, 담당자, 유입경로 배지, 상태.
• 상태 버튼: 각 행에 [내원] [노쇼] [취소] [변경] 큰 버튼. 클릭 1회로 저장, 실수 대비 5초 내 '되돌리기'.
• 자동 강조: 예약 시각이 지났는데 미입력인 행은 주황, 유예시간까지 지나면 빨강 + 상단 알림.
• 빠른 검색: 전화번호 뒷자리 4자리로 즉시 찾기. 예약 없이 온 고객은 [워크인 등록]으로 바로 내원 처리.
• 태블릿·키오스크 옵션(2차): 고객이 직접 QR·번호로 체크인하면 프론트 보드에 자동 반영.
4-3. 입력 규칙
1. 상태 변경 시 입력자 계정, 시각, 이전 상태를 이력으로 자동 저장한다(수정 불가 로그).
2. 노쇼 처리는 예약 시각 + 유예시간(병원 설정, 기본 30분) 이후에만 가능하다. 그 전에는 버튼이 비활성화된다.
3. 노쇼·당일취소 선택 시 사유 1개 선택(연락두절/개인사정/타병원/기타)을 필수로 받는다.
4. 하루 마감 시 미확인 건이 남아 있으면 마감 버튼이 경고를 띄운다. 관리자만 강제 마감 가능.
5. 상태 수정은 당일은 프론트 권한, 익일부터는 관리자 권한으로 제한한다.
4-4. 내원 데이터로 나오는 통계
• 일·주·월별 실내원율(내원 ÷ 예약), 노쇼율, 당일취소율, 지각률
• 유입경로별(전화·홈페이지·플랫폼 앱·소개) 예약 대비 실내원율 → 마케팅 채널의 실제 성과
• 의사·상담실장·시술 항목·요일·시간대별 노쇼율 → 예약 정책 조정
• 노쇼 반복 고객(예: 3회 이상) 자동 표시 → 예약 시 경고, 선결제 안내 대상
• 리마인더 응답 여부와 실제 내원의 상관 → 해피콜 대상 선정
5. 전체 기능 목록 및 우선순위
MVP는 '예약 → 내원 확인 → 기본 통계'가 끊김 없이 돌아가는 데 집중하고, 메시지 자동화와 외부 연동은 2차로 미룬다.

7. 법규·보안 고려사항
병원 CRM은 일반 CRM보다 동의와 접근 통제가 엄격해야 하며, 설계 단계에서 법률 검토를 받는 것을 권한다(아래는 기획 참고용이며 법률 자문이 아님).
• 마케팅 동의는 분리: 개인정보보호법 제22조는 마케팅 수신 동의를 선택 항목으로 분리하고, 거부해도 기본 서비스를 거부하지 못하게 한다. 예약 동의와 마케팅 동의를 한 체크박스로 묶으면 안 된다(메디칼타임즈).
• 민감정보 별도 동의: 상담 내용, 관심 시술, 증상, 치료 계획처럼 건강 상태를 드러내는 정보는 일반 동의와 구분된 별도 동의가 필요하다(같은 기사). → consultation 테이블은 별도 권한·별도 동의 플래그로 관리.
• 진료정보 제3자 제공 금지: 의료법 제21조는 환자가 아닌 사람에게 기록 열람·사본 제공을 원칙적으로 금지한다. 외부 마케팅 대행사에 고객 DB를 넘기는 기능은 만들지 않는다.
• 환자 유인·알선 리스크: 최근 경찰이 연락처를 모아 병원 예약을 잡아주는 DB 마케팅·TM 업체를 압수수색했다. 유입경로별 성과를 추적하더라도 외부 업체에 '내원 건당 수수료'를 산정하는 용도로 쓰이지 않도록 운영 정책을 둔다.
• 정보성/광고성 메시지 구분: 예약 안내·리마인더는 정보성, 이벤트는 광고성으로 분리하고 광고성은 수신동의자에게만 발송.
• 보안 기본: 휴대폰·주민번호 등 암호화 저장, 역할별 화면 접근, 조회·출력·다운로드 로그, 화면 내 개인정보 마스킹, 비밀번호 주기 변경, 클라우드 사용 시 국내 리전.
8. 덴트웹 연동
덴트웹은 API 형태의 연동이 불가능한 것으로 확인되었다. CRM은 덴트웹과 완전히 분리된 프로그램으로 만들며, MVP는 덴트웹과 분리해 운영하고 '휴대폰 번호 + 차트번호'로 같은 환자를 매칭하는 방식으로 시작한다. 아래 연동 단계 중 1단계(분리 운영)만 적용하고, 2~3단계는 덴트웹 정책이 바뀔 때를 위한 참고로 남긴다.
확인된 사실
• 덴트웹의 'Open API' 메뉴는 통신사 발신번호 표시(CID) 서비스용으로, 전화가 오면 덴트웹에 환자 정보를 띄우는 기능이다(덴트웹 게시판).
• 네이버 예약 연동 메뉴도 덴트웹 환경설정에 있다(덴트웹 게시판).
• 외부 CRM이 덴트웹 예약·환자 데이터를 읽고 쓰는 공개 연동 규격은 검색으로 찾지 못했다 → 덴트웹 고객센터(1899-8993)에 직접 문의 필요.

9. 배포 방식
권장안: AWS 서울 리전에 웹 기반 CRM을 올리고, 접속은 병원 IP와 VPN으로만 허용한다. 전담 IT 인력이 없는 1개 지점 치과에서는 원내 서버를 직접 지키는 것보다, 암호화·백업·이중화가 기본 제공되는 클라우드를 제대로 잠그는 편이 더 안전하고 관리 부담이 적다.
초기에는 비용을 줄이기 위해 서버 1대(EC2 t4g.small)로 시작한다. 웹 방화벽 대신 보안 그룹의 IP 허용 목록을, 관리형 VPN 대신 서버에 설치한 WireGuard를 쓴다. 인스턴스와 월 비용은 '비용 계획' 탭에 정리했다.
APK(앱)는 '배포 방식'이 아니라 '화면 형태'의 선택
APK는 안드로이드 앱 설치 파일일 뿐이고, 데이터는 결국 원내 서버든 AWS든 어딘가의 서버에 저장된다. 따라서 결정 순서는 **① 서버 위치(원내 vs AWS) → ② 화면 형태(웹 vs 앱)**다.
• 프론트 데스크는 PC를 쓰므로 **웹(브라우저)**이 기본. 설치·업데이트가 필요 없고, 데이터가 PC에 남지 않는다.
• 태블릿 체크인·원장 모바일 조회는 같은 웹을 반응형으로 만들고, 필요해지면 웹을 감싼 앱(PWA 또는 APK)으로 확장한다. 서버가 같으므로 연동은 자동으로 된다.
• APK를 플레이스토어 없이 직접 설치시키면 위·변조 앱 위험과 업데이트 누락이 생긴다. 환자용 앱은 스토어 배포가 원칙.

10. 보안 설계
보안의 출발점은 「개인정보의 안전성 확보조치 기준」이다. 이 고시는 반드시 지켜야 하는 최소 기준이며, 병원은 보유 규모와 정보 유형에 맞춰 그 이상을 적용해야 한다(고시 요약).
법정 최소 기준에서 CRM에 바로 반영할 것
• 내부 관리계획 수립·시행, 개인정보 보호책임자가 연 1회 이상 이행 점검(고시 제4조).
• 암호화: 비밀번호는 일방향(해시) 암호화, 고유식별정보는 저장 시 암호화, 인터넷으로 주고받을 때 암호화(HTTPS).
• 접속기록: 누가·언제·어디서·어떤 환자 정보에 무슨 작업을 했는지 기록. 민감정보(건강 정보)를 처리하는 시스템은 2년 이상 보관하고 위·변조를 막아야 한다.
• 접근권한: 업무별 최소 권한, 권한 변경 이력 보관, 퇴사자 즉시 차단.

11. 기존 CRM 데이터 이관
데이터를 받아서 새 CRM에 넣고 검증까지 끝낸 뒤에 기존 업체와의 계약을 종료한다. 일부 의료 소프트웨어 약관은 계약 만료 시 데이터베이스 삭제나 데이터 소유권을 업체 쪽으로 규정하기도 하므로, 해지 통보 전에 계약서부터 확인한다(데일리벳).
해지 통보 전 확인할 것
[ ] 계약서·약관의 데이터 소유권, 계약 종료 후 데이터 반환 조항, 반환 비용
[ ] 내보낼 수 있는 항목과 형식(엑셀/CSV/DB 백업), 예약 이력·상담 기록·동의 이력·문자 발송 이력 포함 여부
[ ] 반환 일정과 방법(암호화된 파일 + 비밀번호는 별도 경로로 전달)
[ ] 이관 완료 후 기존 업체의 데이터 파기 확인서 수령 (기존 업체는 개인정보 처리 수탁자이므로 위탁 종료 시 파기 확인 필요)
이관 절차
1. 샘플 추출: 100건 정도 먼저 받아 항목 구조 파악, 필드 매핑표 작성(기존 항목 → 새 CRM 항목).
2. 정제: 전화번호 형식 통일, 중복 고객 병합(전화번호 + 이름 + 생년월일 기준), 덴트웹 차트번호 매칭, 주민등록번호 등 불필요 정보 제거.
3. 시험 이관: 테스트 서버에 전체 데이터 적재 → 건수 대조(고객 수, 예약 수, 상담 수), 무작위 30명 원본과 1:1 대조.
4. 동의 이력 처리: 마케팅 수신 동의 일시·근거가 없는 고객은 '동의 미확인'으로 넣어 광고성 발송 대상에서 제외.
5. 본 이관 + 병행 운영: 오픈 직전 최종 데이터로 다시 적재, 1~2주 기존 CRM을 '조회 전용'으로 두고 새 CRM에서 업무.
6. 종료: 이상 없으면 해지, 받은 원본 파일은 암호화 보관 또는 정해진 기간 후 파기, 업체 파기 확인서 보관.
이관 과정의 원본 파일은 개인 PC·메신저·이메일로 옮기지 않고, 암호화된 저장소 한 곳에서만 다룬다.
12. 개발 로드맵과 다음 단계
먼저 프론트 직원과 함께 '오늘의 내원 보드' 화면을 검증한 뒤 MVP를 만들고, 실제 운영 데이터로 노쇼율이 잡히기 시작하면 메시지 자동화로 넘어간다.
1. 현장 조사: 프론트·상담실 직원 인터뷰, 현재 예약/내원 기록 방식(엑셀·종이·기존 차트) 수집, 하루 예약 건수와 노쇼 빈도 파악.
2. 화면 설계: 내원 보드·예약 캘린더·고객 상세 화면 와이어프레임 → 프론트 직원 테스트.
3. MVP 개발: 고객·예약·내원 확인·상담·기본 통계·권한 (5장 MVP 항목).
4. 시범 운영: 1개 지점(또는 1개 진료실)에서 기존 방식과 병행 운영, 입력 누락률 확인.
5. 2차 개발: 알림톡 리마인더, 리콜 할 일, 원내 동선, 수납 연계.
6. 3차 개발: 전자차트·예약 플랫폼 연동, 셀프 체크인, 마케팅.
