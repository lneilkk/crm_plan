## S. 화면·권한 구조 정리 (확장 계획 1장, [EXPANSION.md](EXPANSION.md)) — 지금 진행 범위

S Task가 끝날 때까지 새 기능은 멈추고, 새 피드백은 FEEDBACK.md에 적어만 둔다. 동작을 바꾸지 않는 정리(S-2·S-3·S-6)와 화면이 달라지는 변경(S-4·S-5)은 한 커밋에 섞지 않는다.

결정 (사용자, 2026-11-13, S-1 조사 후):
- 진료 부서 안에 직무(의사·간호)를 둔다. 직무마다 기본 권한이 다르다. 지금의 역할 값(staff.role)이 곧 직무이고, 부서는 직무에서 정해진다(프론트→프론트, 상담→상담, 의사·간호→진료, 관리자→운영).
- 원장은 진료 부서(의사 직무)에 개인 추가 권한(통계·실적 보기, 상담 보기)을 준다. 운영 부서에 두지 않는다.
- 진료 부서의 첫 화면·메뉴는 S-4에서 기존 화면(내원 보드·예약 캘린더 등)으로 둔다. '오늘 진료 일정'·'수술 기록' 화면은 S가 끝난 뒤 별도 Task로 만든다.

결정·권고 (사용자, 2026-11-13, S-2 보고 후):
- S-2는 시험 서버에 먼저 배포해 확인한 뒤 S-3으로 넘어간다. 마이그레이션이 있는 배포 전에는 서버 DB를 백업한다(`infra/prototype/db-backup.sh`, docs/DEPLOY.md 6장).
- 진료 부서의 첫 화면은 S-4에서 기존 예약 캘린더(일 보기)로 연결한다.
- 예약 금액 노출은 S-5까지 미루지 않고 S-3에 포함한다. 권한이 없는 사람에게는 화면뿐 아니라 API 응답에서도 금액(단가·할인율)을 뺀다. **누가 금액을 볼지 확정 필요** — 제안: 상담·운영·원장.
- S-7: 직무를 바꿀 때 추가 권한을 지우거나 다시 확인받게 한다(화면에 보이게만 하지 않는다). 그때까지는 추가 권한이 있는 계정(지금은 의사 계정)의 직무를 바꾸지 않는다.

결정 (사용자, 2026-11-13, 권한 설정 위치):
- 권한의 종류(각 화면·API가 요구하는 권한)만 프로그램에 둔다. 직무별 권한과 개인 추가 권한은 DB에 두고 관리자가 편집한다(S-2b, S-7).
- 처음 설치할 때의 직무별 권한은 마이그레이션이 DB에 한 번만 넣는다. 시드·재시작·재배포는 관리자가 바꾼 값을 덮어쓰지 않는다.
- 예약 금액 보기: 기본값은 상담·운영·원장. 관리자가 나중에 바꿀 수 있다(S-3에서 권한으로 추가).
- S-7은 직무 × 권한 편집 화면(표에 체크)과 개인 추가 권한 편집으로 넓힌다.
- 설정으로 풀 수 없게 프로그램이 고정하는 것:
  1. 권한 관리 권한(staff.manage)을 가진 활성 직원이 0명이 되는 변경은 거부한다.
  2. 권한 변경은 감사 로그에 남고 관리자도 지울 수 없다.
  3. 감사 로그·내원 상태 이력의 수정·삭제 권한은 존재하지 않는다(줄 수 없음).
  4. 민감 권한(상담 보기, 수술 메모, 가져오기·내보내기 등)을 줄 때는 확인 창을 한 번 더 띄운다(S-7).
  5. 새로 생기는 권한은 기본이 꺼짐이다. 처음부터 주는 경우는 그 권한을 넣는 마이그레이션에 이유를 적는다(예: S-3 예약 금액 보기 — 모두가 보던 것을 줄이는 변경).
- 약점: 관리자 계정 하나가 뚫리면 모든 권한을 열 수 있다 → R3의 T2-2(관리자 2단계 인증)가 더 중요해진다.

결정 (사용자, 2026-11-13, S-2b 확인 후):
- S-3 금액: 보기뿐 아니라 고치기도 막는다. 금액 권한이 없으면 할인율을 바꾸는 요청을 서버가 거부한다. 보내지 않은 값(단가·할인율)은 기존 값을 유지한다(빈 값으로 덮어쓰지 않음).
- S-3 금액이 새는 곳 전부 확인: 예약 상세·목록·캘린더, 상담 → 수술예약 전환 응답, 가져오기 결과 등. 권한 없는 직무로 모든 조회 API를 불러 응답에 단가·할인율이 없는지 검사하는 테스트를 넣는다.
